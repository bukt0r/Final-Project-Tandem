## Code Review
Разбирался в коде бэкенда в папке `server`, написанным @user0k.

**Что вообще смотрел и что понял**

Начал с того, откуда всё стартует. Открыл `main.ts` - там поднимается приложение, все запросы идут по адресам с префиксом `api` (то есть наш фронт дергает например `http://localhost:3000/api/questions`). Порт берётся из настроек. Ещё там включена какая-то проверка входящих данных (ValidationPipe) - в общих чертах понял, что лишние поля из запроса могут отсекаться.

Потом смотрел, как всё разложено по папкам. В корне модулей есть `app.module` туда подключены куски по темам: база, вопросы, топики, пользователи. В каждой такой части есть controller (принимает запросы) и service (делает работу с данными). Для меня важно было понять: какие адреса есть и что они отдают.

Посмотрел схему базы в `prisma/schema.prisma`. Там три сущности: вопросы (заголовок, сложность, даты), топики (название, описание), пользователи (почта, пароль, логин). Вопросы и топики связаны - один вопрос может быть в нескольких топиках, в топике много вопросов. Как это точно хранится в таблицах, я не разбирал, но понял, что на выходе у вопроса есть список id топиков

Дальше именно то, с чем я работаю -вопросы. В `questions.service` при создании и обновлении вопроса проверяется, что все переданные id топиков существуют. Если написать несуществующий id сервер вернёт ошибку и напишет, какие id неправильные. Ответ клиенту формируется так: id вопроса, заголовок, сложность, даты и массив `topicIds` - без полных объектов топиков, только id. Этого хватает для нашего списка на фронте, мы как раз маппим это в свою модель через `toQuestion`.

Топики - там в целом просто - создать, получить список, один по id, обновить, удалить. В одном месте при запросе одного топика подгружаются и вопросы в нём - пригодится, если будем делать страницу топика.

Пользователи - пароль в базу не сохраняется как есть. При ответе клиенту пароль не отдаётся вообще - только id, почта, логин, даты. Есть метод для проверки пароля задел под будущий вход в аккаунт.

**Что было непонятно и какие вопросы остались**

Поначалу путался в маршрутах вопросов. Там есть "получить вопрос по id", "по сложности", "по топику". Оказалось порядок объявления маршрутов важен. Если сначала идёт "любой id", а потом "по сложности", то запрос вроде "получить по сложности easy" может восприняться как "получить вопрос с id = difficulty" и вернуть 404. Хочу спросить у ментора, не лучше ли поставить маршруты "по сложности" и "по топику" выше, чем общий "по id".

Ещё заметил: когда получаем все вопросы или один по id, то приходит один формат (с topicIds). А эндпоинты "по сложности" и "по топику" возвращают данные в другом виде (там есть вложенные объекты топиков). Мы эти два эндпоинта пока не используем, но если будем — на фронте придётся обрабатывать два формата. Нужно уточнить, так и задумано или можно сделать один формат везде.

В `main.ts` в сообщении об ошибке заметил опечатку "Server has crushed" вместо "crashed". Нужно предложить поправить.

**Что осталось после разбора**

Какие модули за что отвечают, какие эндпоинты есть по вопросам, топикам и пользователям, в каком виде приходят вопросы (id, title, difficulty, даты, topicIds).

**Итог**

В общем понял, как устроен бэкенд с моей стороны: откуда берётся список вопросов, почему в ответе есть topicIds и как они проверяются при создании, обновлении. Этого достаточно, чтобы спокойно работать со списком вопросов. Остались два момента для обсуждения: порядок маршрутов в вопросах и одинаковый ли формат ответа нужен для всех способов получения вопросов.
